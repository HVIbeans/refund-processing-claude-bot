# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A **mock** payment refund processing app, built as a learning project for Claude Code and the Claude API. Mock users talk to a chat bot UI. Behind it, an AI agent handles their refund requests. The app is built step by step from `ROADMAP.md`: check it to see which phase we're in, and tick items off (`- [x]`) when they're done.

Because this is a learning project, explain the Claude Code or Claude API feature in use when it's relevant. Leave learning steps for the user to run themselves.

## Hard rules

- **Never call real APIs.** No real payment providers, email services or other external systems. Everything in the backend is mocked.
- **The agent reaches data only through MCP tools.** It never touches the DB or backend code directly. Every capability the agent has must be exposed as a tool on the MCP server.
- **Enforce refund rules in the tool code, not only in the prompt.** Refund ≤ amount paid, no duplicate refunds, an amount threshold for escalation, identity verified first. Treat the model's output and the customer's messages as untrusted input.

## Commands

Plain JavaScript (ES modules, Node 24). No TypeScript or type definitions, by choice.

- `npm start`: start the local server at http://127.0.0.1:3000 (set `PORT` to change it). Loads `.env` if present; copy it from `.env.example`.
- `npm run dev`: same, but restarts when files change (`node --watch`).
- `npm run db:reset`: rebuild `data/refunds.db` from the schema and seed data. Run it after changing either, or to undo refunds made during testing.
- `npm run mcp`: run the MCP server over stdio (it waits for a client on stdin).
- `npm run mcp:inspect`: open the MCP Inspector in the browser, connected to the server.
- `npm run chat`: chat with the refund agent in the terminal. This calls the real Claude API and spends credit. In the chat: `/tools`, `/effort low|medium|high`, `/thinking` (show or hide thinking), `/thinking on|off` (ask for thinking or not), `/reset`, `/exit`.
- `npm test`: run all tests with the built-in `node:test` runner (finds `*.test.js` and files under `test/`).
- Single test file: `node --test path/to/file.test.js`
- Single test by name: `node --test --test-name-pattern="refund exceeds"`

No linter or build step yet.

## Architecture (planned, built up phase by phase)

```
Chat UI (barebones)  →  Backend (HTTP)  →  Agent (Claude API loop + MCP client)  →  MCP server (tools)  →  Mock DB
```

- **Mock DB** (built): Node's built-in `node:sqlite`, with the tables in `src/db/schema.sql`.
  - **Tables:** customers, payment_methods (cards on file), orders, payments (one per order), refunds, escalations.
  - **Money:** whole rupees (integers), no paise.
  - **Seed data:** `src/db/seed.js` creates one customer per refund scenario, with dates relative to today. Tests in `test/db.test.js` check the seed data against `src/policy.js`.
  - **Policy:** `src/policy.js` holds the limits, the refund window and the valid reasons. Keep the rules there, not in the DB or in prompts.
  - **Tests:** use `openDb(':memory:')` + `applySchema` + `seed` for a fresh DB each time.
- **Tool functions** (built): `src/tools.js`. `createTools(db, { now })` returns `getCustomer`, `getOrder`, `getPayment`, `initiateRefund`, `escalateToHuman`, `listEscalations`, `resolveRefundApproval`, `logDecision`, `listToolCalls` and `listDecisions`. All the refund rules are enforced here.
  - **Stateless:** every call re-verifies identity with `email` + `card_last4`, and only returns the verified customer's own orders.
  - **Results:** `{ ok: true, ... }` or `{ ok: false, error: '<code>', message }`. Error codes are stable, and tests assert on them.
  - **Don't leak existence:** an unknown email, a wrong card and someone else's order all get the same reply as a plain miss.
  - **Approval limit:** applies to an order's running total of refunds (completed + pending), so splitting a refund doesn't bypass it. No tool result includes the limit (the model sees every result and could quote it), so `initiateRefund` applies it without showing it.
  - **Human-in-the-loop (step 17):** `listEscalations`/`resolveRefundApproval` are for a human reviewer, not the customer-facing agent — approving its own escalated refund would defeat the point. `resolveRefundApproval` only acts on open `refund_approval` escalations (`account`/`risk` stay open; different shape of problem, not this step's scope), sets the refund to `completed`/`rejected` with `resolved_by: 'human'`, and resolves the escalation, all in one transaction. `refundResult()` (shared with `initiateRefund`) now covers all three refund statuses in its message.
  - **Concurrent-write guardrail (step 18):** two writers can be separate processes on the same `data/refunds.db` (Claude Code's `refund-tools` server and `npm run chat`'s child server). So every tool that writes (`initiateRefund`, `resolveRefundApproval`, `escalateToHuman`, `logDecision`) runs its checks *and* its `nextId()` inside the same `inTransaction(fn, retryMessage)` (`BEGIN IMMEDIATE`) as the write. The exception is the best-effort `tool_call_log` insert in `audited()`, which isn't in a transaction: a lost entry under contention is a known gap. With the lock, no other writer can commit in between, which would let two refunds both pass the approval limit, an approve overwrite a concurrent reject, two escalations of one case both be created, or two rows get the same ID. Lock contention (`SQLITE_BUSY`, `errcode 5`) becomes `{ error: 'try_again', message }`; the MCP instructions tell the model to retry a `try_again` (for `initiate_refund`, with the same idempotency_key), as the exception to "don't retry". The DB trigger `refund_total_guard` (`schema.sql`) is a last backstop for "refunds never exceed what was paid": since the checks run under the lock, it firing means a bug in them, so it is *not* retried and surfaces as `internal_error`. Tested with two real connections to the same temp file (`:memory:` is private per connection); the race tests use the `now` clock, read during the checks, to fire the competing write mid-call.
  - **Audit log (step 19):** `tool_call_log`/`decision_log` (`schema.sql`). Every function `createTools()` returns is wrapped by `audited()`, so every tool call is logged — by whichever consumer called it (the customer-facing agent or a human reviewer) — with its input/output/`is_error`; an exception is logged too, then rethrown, so `server.js`'s existing error handling is unaffected. Logging itself is best-effort (wrapped in its own try/catch): a write-lock conflict while logging must never stop the real result from being returned. `listToolCalls`/`listDecisions` order by `at DESC, rowid DESC` — `rowid`, not `id`, as the tiebreaker, since two calls can share a timestamp (a fast burst, or a fixed clock in tests) and `id` sorts lexicographically past `TCL-9`. `logDecision` is called directly by `repl.js` after `chat.send()` returns a decision — bypassing the LLM entirely, since whether a decision gets logged must never be the model's call; it's validated the same as any MCP input despite not being agent-facing.
  - **Tests:** `test/tools.test.js`. Pass a fixed `now`, as the window-boundary test does. A DB row from `node:sqlite` has a null prototype, so a test comparing one with `assert.deepEqual` must spread it (`{ ...row }`) first.
- **MCP server** (built): `src/mcp/server.js` holds `createMcpServer(tools)`, which wraps each function as a tool: `get_customer`, `get_order`, `get_payment`, `initiate_refund`, `escalate_to_human` and `log_decision`. With `{ reviewer: true }` (`src/mcp/stdio.js --reviewer`) it also registers the human-reviewer tools: `list_escalations`, `resolve_refund_approval`, `list_tool_calls`, `list_decisions`.
  - **Two roles, enforced on the server:** the agent's server (`stdioTransport()`, no flag) doesn't have the reviewer tools at all, so the agent can't approve its own escalated refunds. Claude Code (`.mcp.json`) and `npm run mcp:inspect` pass `--reviewer`.
  - **Schemas:** inputs are zod schemas. Results are JSON text, with `isError: true` when `ok` is false.
  - **Instructions and descriptions** are sent to the model, so keep them short. The shared `instructions` string reaches every client, including the customer-facing agent (via its system prompt) — never mention the reviewer tools there.
  - **Entry point:** `src/mcp/stdio.js` runs the server over stdio. It creates and seeds the DB if it's missing. **Never write to stdout in the server**, because stdout carries the protocol; use `console.error`.
  - **Tests:** `test/mcp.test.js` runs a real `Client` against the server over `InMemoryTransport`.
  - **In Claude Code:** registered for the project in `.mcp.json` as `refund-tools`, so the tools appear here as `mcp__refund-tools__*` and use the real `data/refunds.db`.
    - **Permissions:** the read-only tools (`get_*`, `list_escalations`, `list_tool_calls`, `list_decisions`) are allowed in `.claude/settings.json`. `initiate_refund`, `escalate_to_human` and `resolve_refund_approval` ask first (outside auto mode) — for `resolve_refund_approval` that's the point: a human (here, you via Claude Code) reviews and approves/rejects a refund `initiateRefund` deferred for being above the auto-approve limit.
    - **Test refunds** made from Claude Code change the real DB. Undo them with `npm run db:reset`.
- **Agent** (in progress, `src/agent/`): runs the Claude API tool-use loop and calls the MCP server's tools through an MCP client. Holds the refund policy in its system prompt.
  - **`systemPrompt.js`:** `buildSystemPrompt(policy, { toolInstructions })` is generated from `src/policy.js`, plus the MCP server's instructions under "Tool notes". Keep it deterministic (no dates or IDs) so it can be cached. It must not reveal the internal approval limits.
  - **`chat.js`:** `createChat({ client, model, system, tools, callTool, onToolCall, onText, onDiscard })` runs the hand-written tool loop. Each API call is streamed with `messages.stream()`: text pieces go to `onText` as they arrive, and `finalMessage()` gives the complete message the loop works from (tools only run from finished messages). Separate text blocks get a line break between them. Replies we write ourselves (refusal, empty, cut-off tool call) come back with `fallback: true`, since they were never streamed; if text of a discarded reply was already streamed, `onDiscard` fires so the caller can withdraw it (the REPL prints "(that reply was withdrawn)"). The loop: on `tool_use` it runs each tool in order (a name not in its `tools` list gets an `is_error` result and never reaches `callTool`, since the model's output is untrusted), sends all results back in one user message, and repeats until the model answers. After `maxRounds` it forces a text answer with `tool_choice: none`. It appends the full `response.content` (thinking and `tool_use` blocks included). On a failure it rolls back only to the last completed tool round, because those tools already ran; the next user text then joins that trailing `tool_result` message. `usage` is summed over every API call in the turn.
  - **Connection retry (step 20):** one extra automatic retry, specifically for a dropped connection (`err instanceof Anthropic.APIConnectionError`), inside the per-round attempt loop — safe because a failure already rolls back to a known-safe state. Not for `RateLimitError`/`AuthenticationError`/other `APIError`s (retrying blindly doesn't fix those), and the SDK itself already retries 429/5xx/connection errors internally before any of this runs. `toolRunnerChat.js` doesn't get this — it's the comparison backend from step 16, not the production one.
  - **Prompt caching:** `cache` (default `false`; `setCache` toggles it) marks the system prompt and the last tool definition with `cache_control: { type: "ephemeral" }` — both are byte-identical on every request for the session, so caching them is pure upside (a cache read costs ~10% of normal input price, a write ~1.25×). Generally available: no beta header needed. The growing `messages` history is deliberately *not* cached (would need block-array message content and touches many exact-shape tests); only `src/agent/decision.js`'s extraction call is set up to share this prefix, by receiving the same cached `system` plus the same cached tools (with `DECISION_TOOL` appended after the breakpoint) when `cache` is on.
  - **`mcpClient.js`:** `connectMcp(transport, { reconnect })` connects an MCP client, lists the server's tools and converts them with `toClaudeTool()` into Claude tool definitions (`name`, `description`, `input_schema`). Its `callTool(name, input)` returns `{ text, isError }`; policy failures and invalid input are `isError` results, not exceptions. `stdioTransport()` runs `src/mcp/stdio.js` as a child process, so the agent uses the real `data/refunds.db`. The child gets the SDK's default environment allow-list, not our API key.
    - **Auto-reconnect (step 20):** if the server process dies mid-conversation, `callTool` transparently respawns it and retries the call once, using `client.onclose`/`onerror` (confirmed with a throwaway script: `onclose` fires synchronously on disconnect, and a call afterward throws `Error: Not connected` immediately rather than hanging) to tell a dead connection apart from a normal `isError` result, which resolves fine and must never trigger a reconnect. `reconnect` is a factory (`repl.js` passes `stdioTransport` itself, called again to spawn a fresh child) — without it, a lost connection surfaces a clear error instead, as before. The returned `client` is a getter, not a one-time snapshot, since `reestablish()` reassigns it on reconnect — same reason `close()` already closes over it rather than capturing it by value.
  - **`toolRunnerChat.js`:** the same `createChat`-shaped interface, backed by the SDK's beta `client.beta.messages.toolRunner()` instead of the hand-written loop (roadmap step 16, to compare the two). Each MCP tool is wrapped with `betaTool()` (`@anthropic-ai/sdk/helpers/beta/json-schema`) into a `run()` function; a thrown error becomes an `is_error` tool_result automatically (confirmed from the SDK's own source, `node_modules/@anthropic-ai/sdk/src/lib/tools/BetaToolRunner.ts` — worth reading directly when a beta helper's behavior isn't nailed down by its docs). One `toolRunner()` call is scoped to one customer turn (created with the full history so far, same stateless-per-call shape as `chat.js.send()`); after it finishes, `runner.params.messages` holds the full transcript including every tool round, which is copied into our own `history` so the next turn's new runner has full context. Thinking, effort and caching (`cachedSystem`/`cachedTools`, mirroring `chat.js`) pass straight through, since the runner is a thin wrapper over the same `messages.stream()` request shape. Deliberately **not** ported: `chat.js`'s refusal/empty-reply/cut-off-tool-call fallbacks, history rollback on a failed request, and the `onDiscard` mechanism — `fallback` is always `false` here. Selected in the REPL via `ANTHROPIC_LOOP=runner`.
    - **Comparison:** `chat.js` is 250 lines, `toolRunnerChat.js` is 174 despite duplicating rather than sharing `pushUserText`/`runDecision`/the cache helpers — the real gap is the loop body itself (~90 hand-rolled lines of `rollback`/`discard`/`finish` vs. ~15 lines of `for await`). The Tool Runner also runs every `tool_use` in a round **concurrently** (`Promise.all`), where `chat.js` deliberately runs them one at a time, in order, because refunds have side effects. Use the Tool Runner for a straightforward agent where "call tools until done" is the whole requirement, independent read-only lookups benefit from running in parallel, and a beta dependency is acceptable; use the manual loop (the default here) when tool order/side-effects matter and you need specific recovery behavior from a bad turn rather than just surfacing it raw — i.e. for anything production-shaped, which is this project's actual direction.
  - **`repl.js`:** the terminal front end (`npm run chat`). It starts the MCP server at launch, prints replies as they stream in, prints a dim `↳` line for each tool call and for the extracted decision, and shows the token usage and API calls per turn, plus a `cache: N read / N write` breakdown whenever either is nonzero. `/tools` lists the tools and their token cost. `/decision on|off` toggles decision extraction and `/cache on|off` toggles prompt caching (both on by default here). `ANTHROPIC_LOOP=runner npm run chat` switches to `toolRunnerChat.js`; the startup banner shows which loop is active. Thinking streams in dim after `thinking> `. Refunds made in the chat change the real DB (`npm run db:reset` undoes them). `NOT_FOR_AGENT_TOOLS` filters `log_decision` out of `mcp.tools` before it reaches the model (and `/tools`); the reviewer tools aren't on the agent's server at all. After each `chat.send()` that returns a `decision`, `repl.js` calls `log_decision` directly via `mcp.callTool` (never through the model), wrapped so a logging failure can't break the turn.
  - **`decision.js`:** structured output for the turn's outcome, `{decision, amount, reason, needs_human}`. The Messages API has no JSON-mode, so `extractDecision()` makes a second, separate request after the normal reply: same `system` and `history`, plus one fixed instruction message appended to it — merged into a trailing tool-result message rather than added as a new one, since history can end in a tool round (a `user` message), and two consecutive `user` messages would be rejected. `tool_choice` is forced to `record_decision`. It takes an optional `tools` list to send ahead of `DECISION_TOOL` — `chat.js` passes its cached tools there when `cache` is on, so this call's prefix matches and lands a cache hit, and `DECISION_TOOL` itself (identical every call) picks up its own cache breakpoint in that case too. No `thinking` on this call, since forced tool_choice can't combine with it and none is needed to report an already-made decision. The model's tool input is validated with zod against `MAX_TEXT` (`src/policy.js`); an overlong `reason` is truncated (surrogate-pair safe) rather than discarding an otherwise-valid decision, and a missing or malformed result falls back to `decision: "none"`. This is the model's own self-report, not reconciled against the real tool results — fine for a display line, but step 19's audit log should check against the actual tool_result JSON. `createChat`'s `decide` option (default `false`) gates whether this runs; `setDecide` toggles it mid-conversation. Costs one extra API call per turn, so it's opt-in.
  - **Thinking:** requests ask for adaptive thinking (`thinking: { type: "adaptive" }`, which also thinks between tool calls) and set `output_config.effort`. Both are GA on Sonnet 4.6, with no beta header; don't use the deprecated `budget_tokens`. Thinking blocks (a summary on 4.6, with a `signature`) must be passed back unchanged, which appending the full content does. Thinking is billed as output and counts against `max_tokens` (16,000). `onThinking` receives the streamed thinking; `setEffort` / `setThinking` change later requests.
  - **`capabilities.js`:** `modelSupport(client, model)` asks the Models API (`client.models.retrieve`, free) whether the model supports adaptive thinking and which effort levels, falling back to a built-in list. The REPL only sends `thinking` / `effort` when supported, because other models (e.g. `claude-sonnet-4-5`) return a 400. A reply cut off mid-thinking is rolled back, since its thinking block has no signature yet.
  - **Config:** `ANTHROPIC_API_KEY`, `ANTHROPIC_BASE_URL`, `ANTHROPIC_MODEL` and `ANTHROPIC_EFFORT` (default `medium`) come from `.env`. The base URL is a gateway, so avoid beta headers unless we confirm it passes them through.
  - **Tests:** `test/agent.test.js` uses a fake client, and `test/mcpClient.test.js` connects to the real server over `InMemoryTransport`. Tests never call the real API.
- **Backend + Chat UI**: a minimal chat interface. The backend relays messages to the agent and returns its replies.

## Prompt coach (dev tooling, separate from the refund app)

A `UserPromptSubmit` hook (`.claude/hooks/prompt-coach.js`) reviews each user prompt in a detached background `claude -p` run, using the instructions in `.claude/agents/prompt-coach.md`. Reviews are appended to `.claude/prompt-coach/feedback.md` (git-ignored). The hook prints nothing on purpose, because a `UserPromptSubmit` hook's stdout is added to the main session's context.

The server's `/prompt-feedback` page shows the log live. `src/promptFeedback.js` parses the markdown log, so if you change the review format in the agent file, update the parser and its tests too.

## Policy-reviewer subagent (step 22)

`.claude/agents/policy-reviewer.md` reviews changes to the refund code against the hard rules, using a numbered checklist (rules in tool code, identity, existence leaks, checks inside the write transaction, the reviewer/agent split, hidden limits, layering, stable results). It only has `Read`, `Grep` and `Glob`, so it can't change code, and it can't run git either: pass it the diff (a file path or the text). It loads this `CLAUDE.md` like any session, so when reviewing an old commit, give it snapshot files and expect it to compare against today's notes.

## `/next-step` skill (step 23)

`.claude/skills/next-step/SKILL.md` runs the roadmap workflow: `/next-step` (or `plan`) plans the first unticked numbered step, checking the feature against current docs first, and then asks who builds it. `/next-step done` checks the done-when criteria, runs `npm test`, ticks the step and adds its note here, and shows the diff without committing. Claude can also start it on its own (no `disable-model-invocation`), e.g. on "let's plan the next step".

- **Injected state:** `` !`…` `` lines run before Claude reads the skill (unticked roadmap items, ahead/behind, uncommitted files, recent commits), and their output replaces them. They run in Git Bash here; if one fails, the whole skill aborts.
- **`arguments: [mode]`** puts the first word after the command into `$mode`. **`allowed-tools`** pre-approves only reads, read-only git, `grep` and `head`.
- **Editor warning:** VS Code flags `arguments` and `allowed-tools` as unsupported. That's VS Code's own skill schema; Claude Code supports both (`$mode` was filled in on the first run).
- A new `.claude/skills/` folder needs `/reload-skills` once; edits to an existing skill reload on their own.

## Dev-safety hooks (step 21)

Two more hooks, same plain-Node-ESM-script shape as `prompt-coach.js`, registered in `.claude/settings.json` under `PreToolUse`/`PostToolUse` with matcher `Edit|Write`:

- **`.claude/hooks/protect-policy.js`:** on an edit to `src/policy.js`, prints `hookSpecificOutput: { permissionDecision: "ask", ... }` so it always asks for confirmation — even under `acceptEdits`/auto mode — rather than hard-blocking. `src/policy.js` is the single source of truth for the refund policy, so it gets the same "a human must consciously approve this" treatment as a refund above the auto-approve limit (step 17), without making a genuinely-wanted policy change require editing the hook first. No match on the file path: no output at all, so the hook expresses no opinion.
- **`.claude/hooks/run-tests.js`:** on an edit to a `.js`/`.sql` file under `src/` or `test/`, runs `npm test` and, on failure, prints `{ decision: "block", reason: "..." }` so the failure lands back in context in the same turn — automating the "run tests after changes" discipline this project already follows by hand. Doc-only edits (`CLAUDE.md`, `ROADMAP.md`, ...) are skipped before `npm test` ever runs. Silent on success, same as a passing CI check needs no comment. Uses a single command string with `spawnSync(..., { shell: true })` rather than a separate `args` array, to avoid Node's `DEP0190` deprecation warning.

Both were verified against the real hook mechanism (not just a manual pipe-test): `run-tests.js` via a temporary sentinel-file write proving it actually fires per `Edit` call, `protect-policy.js` by attempting a real edit to `src/policy.js` and confirming a permission prompt appears.
